## [Unreleased]

### Security

- **OAuth `redirect_uri` no longer falls back to spoofable request headers** (`backend/main.py`, `_backend_base_url()`). When `BACKEND_URL` was unset — *or merely left at the `http://localhost:8000` default* — the callback URL advertised to GitHub was built from `X-Forwarded-Host` / `Host`, both client-supplied. Anyone able to set `X-Forwarded-Host` on a request to `/auth/login` (directly, or through an edge proxy that passes client headers through) could make the server advertise an attacker-chosen callback host, leaving GitHub's exact-match callback check as the only remaining defence — a lost layer of defence-in-depth.

  The value now comes from configuration only:
  - An explicitly set `BACKEND_URL` is used verbatim. Critically, a value that *equals* the localhost default now counts as configured; previously it was indistinguishable from "unset", which is what dropped deliberate local configuration into the header fallback.
  - Unset falls back to the localhost default **only** for a genuinely local request with no proxy in front (loopback client, and no `X-Forwarded-Host` / `X-Forwarded-Proto` / `Forwarded` header). So `uvicorn` + OAuth on a laptop still needs no extra configuration.
  - Anything else — proxied, or from a non-loopback client — returns `500` with an operator-facing message instead of guessing, and logs the client and proxy state.
  - `BACKEND_URL` is validated at import (`_resolve_backend_url`): a non-`http(s)` or relative value raises `RuntimeError` at startup rather than reaching GitHub as a `redirect_uri`.
  - A startup warning fires when `GITHUB_CLIENT_ID` is set but `BACKEND_URL` is not, so the misconfiguration surfaces at boot rather than at the first sign-in attempt.
- **Backend URL and env var names removed from user-facing errors** (`frontend/src/utils/errors.ts`). The network-failure message interpolated the configured backend URL and named the variable that sets it, handing anyone who could trigger the error the internal origin and the deployment's config vocabulary. It is now a fixed string. Covered by a regression test.

### Added

- **Per-role yield is persisted and shown on the Results page** (`backend/worker.py`, `backend/store.py`, `backend/main.py`, `frontend/src/views/ResultsView.tsx`). The worker knew how many usernames each role contributed but only streamed it to the SSE log, which is gone by the time anyone opens the results. A role that returns an *empty list* raises nothing, so it produces no warning either — it is indistinguishable from a role that was never requested, which is exactly what a token lacking the scope for it looks like. A `role_counts_json` column now stores the counts, seeded to `0` for every requested role so a role that fails or never reports back still reads as "asked for, got nothing", and persisted on every terminal path (done, cancelled, salvaged-partial, error). The Results page renders them as chips above the charts, with zero-count roles in amber.
- **PDF export cover page** (`frontend/src/utils/pdfTitlePage.ts`). A saved or forwarded report carried no statement of which repository it described. Page 1 now names the repository, when it was collected and exported, how many users it holds (marked `12 of 45 (filtered)` when filters are applied, so the file cannot misdescribe itself), the per-role yield, and — deliberately — **which roles returned nothing**, since that is why a report is short and it is invisible in the charts. Drawn with jsPDF text primitives rather than captured from the DOM, so it stays vector and costs nothing in file size. `toLatin1()` strips characters the built-in WinAnsi fonts cannot encode (the warning strings begin with `⚠️`, which rendered as `&þ` and wrecked the line's letter spacing) and folds typographic punctuation to ASCII rather than deleting it.
- **World map: where inside a country** (`frontend/src/components/WorldMap.tsx`). Clicking a country listed its users under a single label taken from whichever raw location string happened to be seen first, so four users in three cities all appeared to come from one place, and no user's own location was rendered at all. Users are now grouped by the area within the country (`getSubRegion` strips the trailing country from `"Beijing, China"` → `Beijing`), the panel header counts the spread ("4 users across 3 areas"), a chip row isolates one area at a time, and every row shows its own locality.
- **World map coverage footer** (`frontend/src/components/WorldMap.tsx`). A location the resolver cannot place simply vanished from the map, and an incomplete map looks exactly like a complete one. The footer now states the denominator — "38 of 45 users mapped · 7 unrecognised · 3 with no location set" — and both counts are clickable: one panel lists the users whose location could not be placed, with a chip row of the distinct failing strings and their frequencies (one lookup-table entry to add per chip, not per user), the other lists users with an empty profile location.
- **Per-job delete in the Results job picker** (`frontend/src/views/ResultsView.tsx`). A native `<select>` can only hold text, so removing a job meant selecting it first and then finding the bin icon. The picker is now a listbox with an X on each row.

- **Fetch warnings are persisted with the job** (`backend/store.py`, `backend/worker.py`, `backend/main.py`, `frontend/src/views/ResultsView.tsx`). Per-role failures and cap notices were emitted only on the ephemeral SSE queue, so anyone who closed the tab — or simply opened the results later — permanently lost the reason their set came back smaller than expected. This is what made the `iso3166-2` case ("33 stars, 16 users") so hard to diagnose. A `warnings_json` column now stores them, deduplicated, alongside every terminal write; `/results` returns them and the Results view shows an amber banner listing each one.
- **`Retry-After` on 429 responses** (`backend/main.py`). `_rate_check` returned a bare 429, leaving clients to guess between retrying in 1s and 55s. The header now carries the seconds until the oldest hit leaves the window, the message repeats it in prose, and **`expose_headers=["Retry-After"]`** was added to the CORS middleware — without it the header is invisible to the frontend, which is on a different origin in the hosted deployment.
- **Per-owner job retention** (`backend/main.py`, `backend/store.py`). Only a per-minute rate limit existed, so a caller staying comfortably inside it (one request every 3s, indefinitely) could accumulate unbounded job rows, each holding up to `FETCH_LIMIT` profiles — there was a 10-schedule cap but no job equivalent. The newest `MAX_JOBS_PER_OWNER` (default 50, `0` disables) are kept and older ones evicted when a new job is created, cascading to share tokens and schedules so nothing dangles. Pruning is best-effort: a failure logs rather than failing the fetch.
- **Pre-flight cost estimate** (`frontend/src/utils/estimate.ts`, `frontend/src/views/FetchView.tsx`, `backend/models.py`). `FetchRequest.limit` had no upper bound, and a self-hosted install with `FETCH_LIMIT=0` had no ceiling at all. The Fetch form now shows "≈ up to N profiles · about M minutes · ~K API calls" from the role count, limit, worker count and repo count, and switches to an explicit warning when the run is genuinely unbounded. `limit` is additionally capped at 100,000 server-side so a typo cannot request an effectively infinite crawl.
- **Shared results are marked read-only** (`frontend/src/views/ResultsView.tsx`). A share-link job exists only in the recipient's browser, so rename, delete, refresh, share and schedule would all 404 against an id the backend never created. Those controls are now hidden and a "Shared · read-only" badge explains why.
- **Shared modal keyboard handling** (`frontend/src/hooks/useModalEscape.ts`). Only Global Search closed on Escape; the help, recent-results, token-missing, export-picker and world-map country modals did not. One hook now serves all six, with scroll locking where appropriate. It takes a nullable handler, because most of these are inline JSX conditionals rather than components of their own and the hook must be callable unconditionally.

Every place the app explains tokens framed one as a *rate-limit* upgrade, which made `public_repo` read as optional — when it is the difference between 16 users and ~50 on a public repo. The `?` guide's first step now specifies a **classic** token and that `public_repo` is the sub-box *under* `repo`, not `repo` itself (which grants read **and write** on all private repos), lists `read:user`/`user:email` as optional, and says to leave everything else unticked. A new step covers fine-grained tokens, which fail differently: they authenticate fine and then return `403 Resource not accessible by personal access token` on exactly the three roles that matter, needing *Repository access* set to the target repo and `Metadata: Read-only`. The token-field tooltip, the "GitHub Token Recommended" modal and the post-**Check** fine-grained verdict carry the same specifics.

The API table gained the seven endpoints it omitted (share, history, schedules, auth), notes the new `warnings` field and the duplicate-id rejection, and documents rate-limit `Retry-After` and job retention. Added a test-coverage table.

- **`ToDo.md` reconciled with reality.** Eleven items were already implemented but never ticked — filtering and search within results, bot detection, pagination control, virtual scrolling, client-side caching, OAuth, comparison, growth over time, overlap analysis, search history and error-state quality are all shipped and tested. The file now separates genuinely open work (the `repo-blade` rebrand, non-personal-repo verification, and four items carried over from `docs/feature-opportunities.md`) from what is done.

### Dependencies

- **`playwright` added as a frontend devDependency.** Only used by `npm run test:browser`; not part of `npm test`, and the check skips cleanly when it or its browser is absent. Justified by three PDF-export fixes that shipped broken because jsdom structurally cannot model the failure — it does not resolve `color-mix()`, does not serialise computed colours in oklab, and does not run CSS transitions.

### Performance

- **Ownership checks no longer read or parse the result blob** (`backend/store.py`, `backend/main.py`). `_load_job_row()` did `SELECT *` and unconditionally `json.loads(result_json)`, and `_get_owned_job()` called it for *every* job-scoped route — rename, tag edit, delete, cancel, SSE connect, even a cache-hit summary read — whether or not the endpoint touched the payload. Renaming a job on a large fetch re-parsed the whole thing. `_load_job_row(job_id, include_result=False)` now selects an explicit column list that omits `result_json`, and the nine routes that only need metadata use it. `get_summary` reads metadata first and only falls back to the full row on a cache miss. **Measured on a 10,000-user job (6.5 MB blob): 20.1 ms → 1.5 ms per ownership check.** This extends the `logins_json` fix from `[1.1.0]` to the ownership path it never covered.
- **Fetch work moved off the shared thread pool, and concurrent jobs are capped** (`backend/worker.py`, `backend/main.py`). Every blocking GitHub call used `run_in_executor(None, …)` — asyncio's process-wide `ThreadPoolExecutor` of `min(32, cpu_count+4)` threads. The per-job `workers` semaphore bounds concurrency *within* a job; nothing bounded how many jobs ran at once, so a few simultaneous fetches could saturate the pool and starve every other coroutine needing a thread. Fetches now use a dedicated executor (`FETCH_THREAD_POOL_SIZE`, default 24) and a global semaphore caps concurrent jobs (`MAX_CONCURRENT_JOBS`, default 3). A queued job reports "Queued — waiting for a free fetch slot…" on its existing SSE stream rather than sitting silent, and the executor is released on shutdown.
- **SQLite waits longer for a competing writer** (`backend/store.py`). Several jobs finishing together, plus the maintenance and schedule loops, could exceed the driver's 5s default and fail as "database is locked" — surfacing as an unexplained 5xx on a *single* instance, distinct from the documented multi-instance limitation. `busy_timeout` is now 15s (`SQLITE_BUSY_TIMEOUT_MS`), matched by the connect timeout, and `synchronous=NORMAL` removes an fsync per commit (durable under WAL except on OS-level crash). Connection pooling was deliberately not added — a connection per call is cheap for a local file, and the durable answer is Postgres (see `docs/supabase-evaluation.md`).
- **The world map does one pass instead of three** (`frontend/src/components/WorldMap.tsx`). `countryCounts`, `countryUsers` and `countryLabel` were three separate `useMemo`s, each iterating every user and calling `getCountryNum()` — which, for free-text locations, falls back to a whole-word regex scan over ~250 countries and ~400 cities. Now one memo returning all three.
- **Chart aggregates no longer re-run on every page of a background load** (`frontend/src/views/ResultsView.tsx`). Nine `useMemo` aggregates (location, language, org, email domain, health score, funnel, social presence, overlap, growth) were keyed on `users`, and the background page-walk calls `setUsers()` once per page — so all nine O(n) passes re-ran per page over an ever-growing array. They now key on a `chartUsers` snapshot that only advances once loading settles; the table still streams in per page.
- **Inactive views are unmounted rather than hidden with CSS** (`frontend/src/App.tsx`). All three top-level views were toggled with a Tailwind `hidden` class, so switching tabs mid-load left ResultsView's page-walk, history fetch and schedule poll running, and Recharts and the world map re-rendering off-screen. ResultsView and CompareView are now conditionally rendered. **FetchView is deliberately still mounted-but-hidden** — it owns the running job, its SSE stream and the live log, all of which an unmount would destroy.

### Fixed

- **PDF export still failed after the oklch fix, twice more, and the last cause was not a colour at all** (`frontend/src/utils/colors.ts`, `frontend/src/views/ResultsView.tsx`). Three follow-on faults, each hidden behind the previous one:
  1. `color-mix()` was never detected — the gate pattern `color\(` does not match `color-mix(`, and Tailwind v4 compiles every opacity modifier (`bg-white/5`, `hover:bg-white/10`, used throughout) to `color-mix(in oklab, …)`. The gate and the rewriter had also drifted into two separate regexes; they now build from one source.
  2. The property list was hand-written and missed `accent-color` (the table checkboxes), `text-shadow` and every logical border longhand. It is now derived from the computed style by name, so future Tailwind output is covered without editing this file.
  3. The palette override read the **clone's** stylesheets, which in a production build arrive as a `<link>` that has often not parsed when `onclone` fires — leaving the load-bearing half of the shim silently doing nothing. It reads the live document now.

  None of that was the real fault. The shim was writing correct values (`inline: "rgb(229, 231, 235)"`) while the computed value stayed `oklab(0.928 …)`: `.btn-primary`, `.btn-secondary` and every `transition-all` set `transition-property: all`, so **patching a colour starts a transition**, and a colour mid-transition is interpolated in oklab and reported as such regardless of what was written. `freezeAnimations()` now suspends transitions and animations before patching. Measured in a real browser: **59,366 unsupported declarations → 0**, with the freeze disabled → 57. It also fixes the 30 pseudo-element leaks, which no inline style can reach — they were inheriting `color` from transitioning parents.
- **The export button's spinner did not spin** (`frontend/src/utils/colors.ts`, `frontend/src/views/ResultsView.tsx`). The animation freeze above was a blanket `*` rule on the live document, which stopped the export button's own `animate-spin` — the one thing on screen saying the export was running sat motionless for its entire duration. It is now scoped to the captured subtree (plus `<html>`/`<body>`, whose colours are also patched), so animations *inside* the report are still frozen and captured cleanly. Separately, the heavy work began in the same tick as `setExporting(true)`, so React never committed and the browser never painted the spinning state at all; two `requestAnimationFrame` yields fix that, and one after `pdf.save()` keeps it up until the blob is handed off.
- **Exported PDF layout: pages cut through cards, a blank final page, and 82 MB** (`frontend/src/utils/pdfPages.ts`, `frontend/src/views/ResultsView.tsx`). The paging loop sliced the canvas every page-height regardless of content, so page 1 began mid-card, page 2 through a chart and page 4 mid-table-row; it drew a full page for whatever remainder was left; and every page drew the *entire* full-height image at a negative offset, relying on the page to crop it.
  - `planPages()` (pure, unit-tested) cuts at legal boundaries and ends on the content.
  - Cuts are taken at each section's **top**, not its bottom, so the 24px `space-y-6` gap stays on the page being finished rather than eating ~10pt from the next one.
  - Containers marked `data-pdf-rows` — the leaderboard stack and the table `<tbody>` — contribute each row's top, so a tall list flows across pages instead of forcing the previous page to end early. Everything else stays atomic; breaking between table rows is normal in print, breaking through a chart is not. Page fill measured **83/96/61/80% → 84/96/99/41%** (the last page is the remainder).
  - Each page carries only its own slice, and the images are JPEG: the same pages measured **68 MB as PNG and 1.1 MB as JPEG at identical resolution**, since PNG cannot compress a dark, gradient-heavy screenshot. An 8 mm margin was added.
- **Newcastle, NSW was placed in the United Kingdom** (`frontend/src/components/WorldMap.tsx`). `NSW` matched nothing — not a country name, not a city, and three letters so the alpha-2 check skipped it — so the resolver fell through to the city map and found the English Newcastle. A `SUBDIVISION_TO_NUM` lookup (Australian states, Canadian provinces, all 50 US state codes) is now consulted before the city fallback. That exposed a second fault in the same path: two-letter codes that are both a country and a US state resolved to the country unconditionally, so **`Chicago, IL` was Israel**. A sibling city segment now casts the deciding vote, falling back to the country reading when nothing corroborates — `Toronto, CA` stays Canada, `Haifa, IL` stays Israel.
- **Role Distribution chart showed nine bars against five labels** (`frontend/src/views/ResultsView.tsx`). At a fixed `height={220}` Recharts silently drops category ticks it cannot fit. `interval={0}` forces every tick and the height now scales with the role count; labels read as words (`commit authors`) rather than raw keys, matching the Contributor Funnel directly below.
- **A chart row left a card-sized hole when only one of its two cards had data** (`frontend/src/views/ResultsView.tsx`). Three rows render both cards conditionally in a `lg:grid-cols-2` grid, so a lone card left the other cell empty — visible whenever a repo has no resolvable languages. `pairGrid()` collapses to a single full-width column in that case.
- **The Columns dropdown overlapped its own labels** (`frontend/src/components/UserTable.tsx`). The panel was `min-w-56` with a two-column grid and no `min-w-0` on the labels, so a long id like `location_normalized` refused to shrink and ran into its neighbour. Widened, three columns, labels truncate with the full id on hover.

- **A tokenless fetch silently collected nothing for three roles, and blamed the wrong thing** (`backend/worker.py`). GitHub now rejects unauthenticated requests for `stargazers` and `subscribers` (watchers) with `401`, and `maintainers` needs collaborator access — so a run without a PAT quietly returned only the roles that work anonymously. On a repo whose community is mostly stargazers that is most of the result set: one 33-star repository came back with 16 users. The 401 message read *"Authentication failed — token is invalid or expired"*, sending people off to regenerate a token they never had. `_classify_role_error` now takes whether a token was supplied and says **"GitHub requires a token for this role — 0 users collected"** instead, including for the `403` variant, while keeping the generic "access denied" wording for roles like `contributors` that *do* work anonymously. Combined with persisted warnings (above), the reason now survives to the results screen.
- **PDF export failed outright on any Tailwind colour** (`frontend/src/utils/colors.ts`, `frontend/src/views/ResultsView.tsx`). Tailwind v4 emits its palette in `oklch()`, and html2canvas 1.4.1 predates CSS Color 4 — it *throws* rather than degrading, so a single such colour anywhere in the report killed the whole export with `Attempting to parse an unsupported color function "oklch"`. All 45 oklch values in the built stylesheet live in `--color-*` custom properties, so the fix converts the **variables**: an unlayered `:root{…}` override is injected into html2canvas's cloned document, which fixes every consumer at once — including `<html>`/`<body>`, whose background it inspects *before* parsing the target subtree. Conversion is done by the browser (paint one pixel, read it back) rather than by hand-rolled colour-space maths, and an element walk remains as a safety net for any non-var oklch. A first attempt that only patched computed element properties did not work: it missed both the variables and the document-level background read.
- **Markdown export crashed on click** (`frontend/src/views/ResultsView.tsx`). `roleDistData.sort(...)` mutated an array derived during render, which React 19 freezes — `TypeError: Cannot assign to read only property '0'`. The same in-place sort also ran *during* render for the "Top Role" card, a latent bug independent of the freeze. Both now sort a copy. A failed PDF export also alerts instead of only logging to the console.
- **Role Distribution chart was unreadable on hover** (`frontend/src/views/ResultsView.tsx`). Recharts' defaults assume a light theme: the tooltip label renders in `#000` — **1.18:1** against the `#111827` tooltip background, effectively invisible — and the bar cursor is an opaque `#ccc` band that washed out the hovered row. Now `#e5e7eb` (**14.33:1**) with a subtle translucent cursor. `itemStyle` is set here too because several palette colours fail AA as text (purple 4.19:1, indigo 3.97:1); it is deliberately *not* a shared default, since on a multi-series chart it would strip the series↔colour association. Six other charts still use the bare default.
- **Shared results links were broken end to end** (`frontend/src/App.tsx`, `frontend/src/views/ResultsView.tsx`, new `frontend/src/utils/localResults.ts`). A `#share=TOKEN` link fetched the rows and stashed them in `allJobUsers[shared-xxxxxxxx]`, but `ResultsView.loadJob` knew nothing about that map and independently called `/results/{tempId}` and `/results/{tempId}/summary`. No such job exists on the backend, so both 404'd and the entire results block — gated behind `{summary && …}` — never rendered: the app's own "send this to a colleague" feature showed the recipient an error screen. Global Search kept working because it reads `allJobUsers` directly, which is presumably why manual testing missed it. `ResultsView` now takes a `localJobUsers` prop and short-circuits the network entirely for those ids, computing the summary client-side. Shared rows are held in a **separate** `sharedJobUsers` map rather than reused from `allJobUsers`, which is a cache of *fetched* jobs and must stay refreshable. Search, filtering and sorting are reimplemented client-side (`filterAndSortUsers`) so the controls are not silently inert for a recipient.
- **Two charts silently dropped the `fork_owners` role** (`frontend/src/types/index.ts`, `frontend/src/views/ResultsView.tsx`). "Contributor Funnel" and "Social Presence by Role" each hard-coded an eight-role order omitting `fork_owners`, one of the nine in `ALL_ROLES` and an ordinary checkbox on the Fetch screen — so anyone whose only role was that one vanished from both charts rather than showing a zero-height row. Both now derive from a single exported `ROLE_FUNNEL_ORDER`, with a test asserting it covers `ALL_ROLES` exactly.
- **The Scheduled Re-fetch panel was not scoped to the selected job** (`frontend/src/views/ResultsView.tsx`). `GET /schedules` returns every schedule for the session across all repos, and the panel rendered them unfiltered: changing the Job dropdown changed nothing, and one repo's panel offered pause/delete for another repo's schedule, distinguishable only by reading the label. Now filtered on `source_job_id`, with a count of schedules on other jobs so they are not simply hidden.
- **Compare columns and the world-map modal were never virtualized** (`frontend/src/views/CompareView.tsx`, `frontend/src/components/WorldMap.tsx`, new `frontend/src/components/VirtualList.tsx`). Both mapped the complete, uncapped list from `/compare`, `/compare/multi` or a country click straight into the DOM — one avatar row each — while the main table had used `@tanstack/react-virtual` for some time. Comparing two large repos, or clicking a populous country, mounted thousands of rows synchronously. A shared `VirtualList` now backs both; lists under 60 rows still render plainly, keeping the DOM natural for the common case.
- **`/compare/multi` accepted duplicate `job_ids`** (`backend/main.py`). A repeated id inflated `n`, shifting the "in all" threshold and splitting one job across two "exclusive" buckets — silently wrong statistics rather than an error. Now `422`.
- **OAuth callback trusted GitHub's response shape** (`backend/main.py`). `token_resp.json()`, `user_resp.json()` and `user_data["login"]` were all unguarded, so a non-JSON body or unexpected payload (a GitHub incident, an intercepting proxy) raised `JSONDecodeError`/`KeyError` and surfaced as a bare `500`. Each now returns a `502` explaining what went wrong, matching the existing "missing access_token" branch. A missing or non-string `login` is rejected specifically, since it is the identity every job is keyed on (`gh:{login}`).
- **TOCTOU race on the ten-schedules-per-owner cap** (`backend/main.py`, `backend/store.py`). The count and the insert were separate operations in the endpoint, so two concurrent `POST /schedules` — a double-click suffices — could both observe an under-cap count and both succeed. The cap moved into `create_schedule()` as a single `INSERT … SELECT … WHERE (SELECT COUNT(*) …) < ?` statement, serialised within the process by a lock because each `_db()` call opens its own connection. A concurrency test firing 16 simultaneous creates now lands exactly on the cap; the same test failed against the first attempt, which used a separate count.
- **Stopping a fetch during SSE reconnect backoff left an orphaned connection** (`frontend/src/views/FetchView.tsx`). The stop check ran only when a reconnect was *scheduled*; `handleStop` closed the live `EventSource`, but an already-queued `setTimeout(connectSSE, delay)` still fired, opened a new stream and overwrote the ref — resuming a fetch the UI had reported as stopped, with no Stop button left to close it. The timer handle is now tracked, re-checked on fire, cleared by `handleStop`, and cleared on unmount along with the stream.
- **Malformed imported data could crash the world map** (`frontend/src/components/WorldMap.tsx`). `u.login[0].toUpperCase()` in the initials-avatar fallback threw on an empty login, and `/import` accepts arbitrary JSON with no per-field validation — so a hand-edited or corrupted export took down the whole Results view, the map having no error boundary tighter than the page. Now falls back to `?`.
- **Help modal listed 7 of 9 roles** (`frontend/src/App.tsx`). "Commit Authors" and "Dependents" were missing from the onboarding copy despite being selectable on the same screen.

### Added

- **Token validation button** (`frontend/src/utils/api.ts`, `frontend/src/views/FetchView.tsx`) — a **Validate** button beside the PAT field checks the token against GitHub before a fetch is started, reporting the account, remaining rate limit, and any missing scope. `validateGitHubToken()` calls `api.github.com/user` **directly from the browser** rather than through our backend: GitHub sends `access-control-allow-origin: *` and exposes `X-OAuth-Scopes` plus the rate-limit headers via `access-control-expose-headers`, so a relay endpoint would only add a second code path handling a live credential. It is deliberately a bare `fetch` — no `credentials`, no CSRF header — since sending our session cookie to github.com would be wrong. Editing the token clears the previous verdict so a stale ✅ cannot sit beside a changed value.
  - **Fine-grained PATs report no classic scopes**, so an empty `X-OAuth-Scopes` header means "cannot tell", not "no permissions". Those get a neutral note rather than a bogus "missing `public_repo`" warning on a token that works.
- **Brand logo at the top of the body** (`frontend/public/logo.png`, `frontend/src/App.tsx`) — the `repo-people` mark, centred above the view content at 192px (144px on small screens). Vendored into `/public` rather than hotlinked from `raw.githubusercontent.com`: that host is **absent from the CSP's `img-src`**, so a remote URL would have loaded in dev and been silently blocked in production. The asset is derived from the upstream logo by flood-filling the background from the corners (the source has no alpha and a near-white background that would render as a white box on the dark page), cropping to the circular mark — the source carries its own "repo-people" wordmark, which would duplicate the header text — dropping disconnected specks, and quantising: **491 KB → 26.5 KB** at 512px, which stays sharp at 192 CSS px on a 2× display.

## [1.1.0] — 2026-08-17

Findings from a full-codebase security and correctness audit.

> **Upgrading from 1.0.x.** Two operational notes: OAuth session tokens are now
> encrypted at rest, so every existing session is invalidated and users must sign
> in once after deploying — set `SESSION_TOKEN_KEY` first, or sessions will also
> be dropped on every restart. And `cloudrun-service.yaml` now sets
> `minScale: "1"`, which is required for scheduled re-fetch to run at all but
> bills continuously.

### Security

- **OAuth login CSRF — the `state` was not bound to the browser** (`backend/main.py`, `backend/store.py`). `add_oauth_state()` wrote the state to a global table and `consume_oauth_state()` only checked that it existed, so the state proved *some* flow had started, not that **this** browser started it. An attacker could hit `/auth/login` themselves, capture their own `?code=…&state=…` callback URL without following it, and get a victim to load it — silently signing the victim into the attacker's GitHub account. Since jobs are keyed `gh:{login}`, everything the victim then fetched landed in the attacker's namespace and was readable by them. `/auth/login` now also sets the state in an httponly, short-lived `rp_oauth_state` cookie, and `/auth/callback` requires a `secrets.compare_digest` match **before** the DB lookup — so a replayed callback cannot consume (and thereby burn) a state belonging to someone else's in-flight login. The cookie is cleared on success.
- **GitHub access tokens are encrypted at rest** (`backend/store.py`). `sessions.github_token` held a live OAuth token (`read:user user:email public_repo`) in plaintext for up to 30 days, so a database dump handed over every user's GitHub credentials. Tokens are now Fernet-encrypted (`_encrypt_token`/`_decrypt_token`) under `SESSION_TOKEN_KEY`; unset falls back to a per-process ephemeral key with a startup warning. `get_session` decrypts on read and **deletes** any row it cannot decrypt (legacy plaintext, or a rotated key), so a ciphertext blob can never be sent to GitHub as a Bearer token. **Existing users must sign in once after deploying.**
- **CSRF on preflight-free mutating routes** (`backend/main.py`, `frontend/src/utils/api.ts`). The documented split deployment (Vercel frontend + Cloud Run backend) requires `COOKIE_SAMESITE=none`, so the browser attaches session cookies to cross-site requests; CORS only prevents an attacker *reading* the response, not the request being delivered. `POST /import` with `Content-Type: text/plain` was a "simple" request and let a third-party page create jobs in a victim's account and burn their rate budget; `POST /auth/logout` and `POST /fetch/{id}/cancel` were nuisance-grade. A `require_csrf_header` middleware now rejects `POST`/`PUT`/`PATCH`/`DELETE` without an `X-Requested-With` header (`403`), which forces a preflight that fails CORS for unlisted origins. `GET /auth/callback` is exempt — GitHub drives that redirect and it is protected by the state cookie instead. The middleware is registered *before* `CORSMiddleware` so CORS remains outermost and the `403` is readable rather than surfacing as an opaque CORS failure.
- **Security headers on the frontend** (`vercel.json`). Added `Content-Security-Policy`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `X-Frame-Options: DENY` and a `Permissions-Policy`. Because the file uses legacy `routes` (which cannot be combined with a top-level `headers` block), they are applied via a `"continue": true` pass-through route. The CSP keeps `script-src 'self'` with no `unsafe-inline`; `connect-src` is `https:` and flagged in-file as the value to tighten to the exact backend origin.

### Fixed

- **Charts, quick-stat badges and client-side exports only ever described the first page** (`frontend/src/views/ResultsView.tsx`, `frontend/src/utils/api.ts`). `users` held only the pages that had been scrolled into view (200 at a time), yet every aggregate derived from it — `healthScore`, location/language/org/email-domain breakdowns, growth, role overlap — silently described that fraction. With the default `FETCH_LIMIT=500` this was the common case, not an edge case. Worse, the "total users" badge rendered `users.length` while the summary card directly above it showed the server's total, so the same screen contradicted itself. `loadJob` now renders page 1 immediately and then pulls the remaining pages in the background via the new `fetchAllResultPages()` helper (capped at `MAX_CLIENT_ROWS = 10000`), guarded by a `loadTokenRef` so a filter change mid-load discards stale pages. The badge reads the server total.
- **Client-side exports silently dropped every unloaded row** (`frontend/src/views/ResultsView.tsx`). Same root cause: "Export JSON/CSV/Excel" and the per-role CSV serialised only the loaded pages, so exporting a 500-row job produced 200 rows with no warning. Export buttons are now disabled until coverage is complete, and a banner states the actual coverage while loading or when a result set exceeds the client cap. Coverage is *derived* from the row count rather than tracked in state, so a page walk that fails part-way is correctly reported as incomplete instead of a flag claiming success.
- **Scheduled re-fetch never fired in production** (`cloudrun-service.yaml`). `_schedule_loop()` is an in-process asyncio loop, but the deployed service set `minScale: "0"` — the instance scaled to zero, the loop died with it, and schedules never ran while the UI still showed them enabled with a sliding `next_run_at`. Set to `minScale: "1"`, documented inline, **including that a warm instance bills continuously**; revert to `0` only if you drop scheduling or move it to Cloud Scheduler.
- **`/schedules` was missing from the Vite dev proxy** (`frontend/vite.config.ts`). Dev requests hit the Vite server and 404'd, and `fetchSchedules()` swallows a failure with `return []` — so scheduling looked empty-but-working locally. Added `/schedules` and `/healthz`.
- **SSE event queues grew without bound** (`backend/store.py`, `backend/worker.py`). Each job got an unbounded `asyncio.Queue`, and the worker emits one event per fetched user whether or not an SSE client is attached. A client that never opened the stream (or disconnected mid-fetch) left every event resident for the life of the process, and `_runtime` entries are only removed on `delete_job`. Queues are now bounded (`_EVENT_QUEUE_MAX = 500`, built by `_new_runtime()`) and `emit_event()` drops the oldest event when full — the terminal `done` event is written last, so it always survives eviction.
- **`GET /jobs/{id}/history` parsed every run's full result blob** (`backend/store.py`). It selected `result_json` for *every* completed run of a repo purely to rebuild each run's set of logins, and `ResultsView` calls it automatically on every job selection — tens of MB of JSON parsing on a hot path for an uncapped local install. ## [Unreleased] — 2026-07-14

### Documentation

- **README.md** — Centered the `repo-people-app` availability line on the main README to improve visual layout and consistency with the project banner.


### Security

- **Jobs are now scoped to their creator (IDOR fix).** Previously every endpoint was unauthenticated and `GET /jobs` listed *all* jobs to *all* visitors, so anyone could read, export, compare, rename, or delete anyone else's harvested data. A new `owner_key` column (`backend/store.py`) scopes each job to its creator — the GitHub login for OAuth users, or an anonymous httponly `rp_client` cookie otherwise. `GET /jobs` filters to the caller (`load_jobs_list(owner_key)`); `/results`, `/summary`, `/top`, `/export/*`, `/compare`, `/compare/multi`, `/share`, `DELETE`, `PATCH`, `/cancel`, and `/stream` all resolve jobs through `_get_owned_job()` and return `404` for jobs the caller doesn't own (existence is not leaked). Legacy jobs with a `NULL` owner remain public for back-compat.
- **`GET /clear_cache` (destructive) replaced by a guarded `POST`.** The old endpoint was a prefetchable `GET` that ran `DELETE FROM jobs` with no auth — any crawler, link prefetch, or `<img>` could wipe the database. It is now `POST /clear_cache`, disabled unless `ALLOW_DEV_CLEAR=1` (returns `403` otherwise). `main.tsx` updated to `POST`.
- **Stored-XSS guard on import.** `POST /import` accepted arbitrary records that the frontend later rendered in `href`/`src`. `_sanitise_urls()` (`backend/main.py`) now blanks any non-`http(s)` `html_url`/`avatar_url`/`blog` value (e.g. `javascript:`, `data:`) before storage.
- **Import size-limit bypass closed.** The 5 MB cap previously trusted the `Content-Length` header (omit it and the body was read unbounded). `_read_capped_body()` now streams the request and aborts at 5 MB regardless of headers.
- **Session cookie flags are environment-driven.** The OAuth session cookie was hardcoded `secure=False`. `Secure` is now auto-enabled when `BACKEND_URL` is HTTPS, and `SameSite` is configurable via `COOKIE_SAMESITE` (`lax` default; `none` forces `Secure`) for cross-origin frontend/backend deployments.
